# Zoo World: проектные договорённости

## Требования пользователя

- Пользователь выбрал **UniState** как основную библиотеку машин состояний.
- Пользователь требует MVVM, реактивность R3, UniTask, NightPool для динамических Unity объектов и точечные тесты. Следовать KISS, SOLID и DRY без абстракций ради принципов.
- Использовать уже установленные UniTask, R3, Zenject/Extenject, NightPool и DOTween там, где они решают задачу. Выбирать пакет по назначению; не создавать лишние обёртки и сервисы только ради использования всех зависимостей.
- Игровая логика и симуляция должны быть отделены от Unity и запускаться в обычном .NET окружении. Unity отвечает за представление, ввод и инфраструктурные адаптеры.
- **WebGL/IL2CPP — целевая платформа**, учитываемая с начала разработки. Пользователь разрешил UniTask для асинхронности.
- Общаться с пользователем на русском языке.
- Тесты и сборки запускать только по явной команде пользователя. После изменений автоматически их не запускать; это правило имеет приоритет над общими указаниями о проверках ниже.
- Не зашивать идентификаторы видов (например, `"snake"`) в игровую логику. Возможности и правила взаимодействий определять по конфигам, чтобы переименование TypeId не меняло поведение.

## Границы архитектуры

- Домен хранит состояние мира, правила, идентификаторы сущностей и результаты симуляции. Зависимости от `GameObject`, `Transform`, `MonoBehaviour`, `Animator`, `UnityEngine.Time`, Unity логирования и Unity ввода остаются во внешнем слое.
- При развитии проекта выделять сборки по реальным границам: Domain, Application, Unity adapters/presentation и Composition Root. Создавать их по мере появления ответственности, без пустых абстракций заранее.
- Приложение координирует сценарии и состояния UniState, используя доменные модели и интерфейсы внешних сервисов. Конкретные Unity реализации и регистрация Zenject находятся снаружи.
- Связи между слоями задавать через конструкторы, команды, события и явные интерфейсы. Доменным сущностям не нужен доступ к `DiContainer`.
- UniState сохранять выбранной FSM. Для строгой независимости адаптировать его ядро в поддерживаемом embedded пакете/форке либо изолировать в слое приложения. Изоляция отделяет домен, но сама по себе не делает UniState независимым от Unity.
- Авторитетные физические позиции рассчитывает Unity Physics через IPhysicsWorld. Domain хранит подтверждённую позу, Application задаёт команды движения. Представление не изменяет Rigidbody. Независимые тесты заменяют физический адаптер и не воспроизводят PhysX.
- DOTween и Timeline управляют представлением. Игровые результаты определяются моделью и сценариями приложения.
- NightPool обслуживает Unity представления. Идентичность и время жизни доменной сущности определяются симуляцией.

## Асинхронность, реактивность и время жизни

- Использовать UniTask и явный `CancellationToken` для длительных операций. Определять владельца операции: приложение, NPC, активное состояние или конкретная активация pooled View.
- При выходе из состояния и возврате View в пул отменять принадлежащие им операции, завершать подписки R3 и tween-анимации. Следующая активация получает новое время жизни; `OnDestroy` недостаточен для pooled объектов.
- Избегать `async void` вне требуемых сигнатур событий. Для запуска без ожидания определять обработку ошибок и владельца отмены.
- Обрабатывать переходы последовательно; исключать переходы из завершившейся операции уже неактивного состояния. При необходимости использовать очередь команд или идентификатор активации.
- Для независимой симуляции передавать часы, шаг времени, случайность и планировщик через параметры/интерфейсы. Тип `UniTask` допустим в независимых API; Unity PlayerLoop ожидания размещать в адаптерах. У .NET версии UniTask API отличается от Unity версии.
- Операторы времени R3 используют явно выбранный TimeProvider/FrameProvider. Их реализация должна соответствовать симуляции и WebGL; не полагаться на фоновые системные таймеры.
- В WebGL исполнять игровую логику без `Task.Run`, `RunOnThreadPool`, `SwitchToThreadPool`, управляемых фоновых потоков и блокирующего ожидания незавершённых задач.
- Использовать R3 для наблюдения и событий с понятным владельцем подписок. Прямые локальные вызовы сохранять там, где поток событий не нужен.

## Текущие точки интеграции

- Пользователь согласовал Unity Physics, DotRecast и uGUI/Canvas вместо старой самостоятельной физики и OnGUI. Следовать актуальной реализации и README.
- Запуск из Bootstrap: SceneContext + BootstrapInstaller собирают сервисы; ZooBootstrap получает их через Inject и запускает ApplicationFlow. Game загружается additively через ZenjectSceneLoader с LoadSceneRelationship.Child. Game содержит свой SceneContext + GameSceneInstaller, заранее собранный уровень и BoxCollider-препятствия. Спавн начинается после подготовки сессии.
- Реализованы Zoo.Domain, Zoo.Application, Zoo.Navigation.DotRecast, Zoo.Navigation.Baking (Editor), Zoo.Physics.Unity, Zoo.Unity, Zoo.Composition и Zoo.Editor. Независимые сборки используют noEngineReferences.
- UniState 1.12.1 — embedded Packages/com.bazyleu.unistate; Core независим от Unity, изменения описаны в PATCHES.md. NPC использует вложенные FSM с явными resolver. Это иерархическая FSM, а не Selector/Sequence Behavior Tree.
- AnimalBrain задаёт жизненный цикл и отмену операций. GroundAnimalBrain и FlyingAnimalBrain реализуют поведение и выбор маршрута; AnimalLifecycle выбирает реализацию по конфигурации движения. Состояния находятся в подпапках States своих владельцев. MovementMachine исполняет планы IMovementBehavior.
- Animals.asset ссылается на AnimalDefinitionSO. Движение, поведение, правила взаимодействий, тело и навигационный профиль — отдельные SO. Правила взаимодействий задаются только по пищевой роли цели через InteractionProfileSO.Roles. В SO нельзя хранить изменяемое состояние экземпляра.
- DotRecast Core/Detour/Recast 2026.3.1 устанавливаются через NuGetForUnity. NavigationBakeSource собирает BoxCollider-геометрию и хеш, NavigationAuthoring запекает NavigationDataSO. NavigationDataValidation используется экспортом и NavigationBuildValidator. Поиск ограничен бюджетом на основном потоке.
- IViewPool изолирует NightPool. Использовать только prefab assets, не runtime-объекты сцены как шаблоны NightPool. Физические тела и View выдаются отдельно. Ёмкость расширяется без перераспределения живых объектов. Prefab животного содержит GameObjectContext и AnimalViewInstaller; AnimalViewPresenter владеет R3-подписками текущей активации. NightPoolViewPool внедряет зависимости клона один раз; повторные выдачи меняют модель через Bind. NightPool активирует клон до injection: не обращаться к внедрённым зависимостям в Awake/OnEnable pooled-компонентов. Конструкторы DI сохранены в Scripts/Composition/link.xml.
- MVVM: R3-потоки обновляют ViewModel/View без общего Refresh; ViewModel не продвигает симуляцию. Физика, активные поиски и анимация продвигаются в инфраструктурном цикле.
- Tools/Headless/Zoo.Headless.Runtime.csproj компилирует те же Domain/Application/UniState Core/Navigation исходники с .NET UniTask/R3/DotRecast. Tests/Headless ссылается на эту сборку и добавляет поведенческие тесты. Unity тесты покрывают физику, загрузку/перезапуск сцен и повторное использование пула.
- Zoo/Export simulation settings to JSON экспортирует настройки Bootstrap, каталог SO и Game в переносимый snapshot версии 2 с interactions.byRole. Версия 1 отклоняется; старые snapshots нужно экспортировать заново. Схема и проверка данных находятся в Scripts/Configuration (Zoo.Configuration, Editor-only в Unity, noEngineReferences). Неизвестные виды движения/правил/поведения должны явно отклоняться или получать полноценный экспорт и загрузку.
- Готовый пример — Exports/zoo-world.json. Tools/Headless/Runner запускает JSON в .NET 8 с реальным DotRecast и BepuPhysics 2.4.0 через IPhysicsWorld. BEPU устанавливается только в .NET-проекты, сохранять их packages.lock.json. Результаты физики могут отличаться от PhysX. Для повторяемого headless-прогона указывать --seed.
- Экспорт включает твёрдые мировые BoxCollider и логические границы площадки из Ground. Пол и навигация продолжаются за границей площадки. GameSession проверяет выход животных раз в секунду симуляции. Геометрия навигации должна быть запечена перед экспортом. Экспорт учитывает текущие правки открытых сцен, закрытые сцены читает через PreviewScene.
- ApplicationFlow публикует ApplicationStatus. LoadingScreenViewModel принадлежит GameObjectContext экрана загрузки. UnitySceneLoadingService загружает дочерний SceneContext, UnityGameSessionHost через SceneContextRegistry получает GameSceneSession; runtime-обходов сцены для поиска зависимостей нет. GameSceneInstaller явно регистрирует GameSceneBindings. GameSceneSession владеет ресурсами Game и допускает одну подготовку; Retry создаёт новую сцену. GameSessionFactory атомарно передаёт физику и навигацию сессии. Камера настраивается в сцене Game; отдельного WorldCameraFraming в текущих исходниках нет.
- Столкновения: GameSession после физического шага публикует R3 `CollisionEvent` с участниками. InteractionResolver владеет подпиской, проверяет IInteraction по порядку enum InteractionType и выполняет первое подходящее. EatingInteraction и BounceInteraction сами вызывают доменное действие/физические команды; отдельного InteractionEffects нет. CanExecute не изменяет состояние и не расходует случайность, поскольку используется также фильтром PhysX.
- GameSession владеет физикой и навигацией после успешного конструктора. AnimalSpawner выбирает вид и место спавна, SpawnScheduler задаёт интервал, AnimalLifecycle управляет телами и FSM животных. При ошибке создания адаптеры освобождает точка сборки, после передачи владения — сессия.
- DOTween применяется к визуальной высоте прыжка; tween завершается при Unbind. EatingInteraction передаёт текст через AnimalMeal.Message и ViewModel в AnimalView. UniTask управляет отменяемым скрытием надписи. При Unbind очищаются текст и операции текущей активации.
- Для изменения препятствий использовать Zoo/Bake current level navigation. Текущая версия Editor содержит инструменты Navigation и Export.

## Работа с зависимостями и проверка

- Собственный контент хранить в `Assets/Zoo World`. Иерархия и назначение папок описаны в разделе «Структура проекта» README.
- Код: `Scripts/Domain`, `Scripts/Application`, `Scripts/Adapters/{DotRecast,UnityPhysics,Unity}`, `Scripts/Composition`. Внутри слоя выбирать предметную категорию; не складывать новые скрипты в корень слоя. Сохранять существующие границы `.asmdef` и независимость Domain/Application.
- Самостоятельные публичные типы размещать в одноимённых файлах. Вложенные состояния FSM сохранять внутри владельца. Папка не требует отдельной сборки или нового namespace.
- SO-классы: `Scripts/Adapters/Unity/Configuration/<Category>`. SO-assets: `Settings/Animals/<Species>` для настроек вида; общие — `Settings/{Movement,Interactions,Behavior,Navigation}`. Каталог животных: `Settings/Catalogs/Animals.asset`.
- Prefab: `Prefabs/{Animals,Physics}`; материалы: `Art/Materials/{Animals,Environment}`; инструменты: `Editor/{Scenes,Navigation}`. Независимый Recast baker — `Editor/Navigation/Baking` со своей Editor-only сборкой и включением в headless-проект.
- При перемещении Unity-assets сохранять `.meta`/GUID, обновлять пути в генераторе сцен, тестах, headless `.csproj` и документации. Не перестраивать демонстрационные сцены ради изменения папок.

- Постоянные изменения сторонних пакетов выполнять через поддерживаемый embedded пакет/форк. `Library/PackageCache` — генерируемый кэш, не место для исправлений.
- Сохранять lock-файл UPM и конфигурацию NuGet. Unity генерирует `.csproj`; зависимости текущего Unity проекта управляются UPM/NuGetForUnity.
- Проверять игровую логику без Unity там, где это возможно; интеграции, пулы и представление — в соответствующих Unity тестах. Добавлять проверки поведения и существенных сценариев, а не копии реализации.
- Для изменений исполнения проверять сценарии в WebGL/IL2CPP с фактическими настройками stripping. Отделять вывод по исходникам от результата реального запуска в браузере.
- Для задач инвентаризации и документации достаточно проверки файлов и фактических данных Editor; не менять сцены, зависимости или игровой код без необходимости для задачи.
